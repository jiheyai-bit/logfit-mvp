# LogFit MVP 설계

## 1. 의도와 해결할 문제

LogFit은 식사와 운동을 기록하려는 사람이 항목을 하나씩 선택하지 않고 한 문장으로 하루를 남기도록 돕는다. 대상 사용자는 직장과 대학원을 병행해 세부 입력을 자주 놓치는 사람이다.

현재의 문제는 다음과 같다.

- 식단을 음식 항목별로 선택해 입력하는 부담이 크다.
- 운동을 했어도 웨어러블 배터리 부족이나 운동 종류 미선택으로 기록이 사라진다.
- 기록이 빠지면 7일 동안의 식사·운동 패턴을 파악하기 어렵다.

## 2. MVP 목표

- 자연어 한 문장으로 식사·운동·휴식을 기록한다.
- AI가 추출한 기록을 저장 전에 사용자가 확인하고 수정한다.
- 오늘의 식사 기록 수, 운동 시간, 휴식 또는 미기록 상태를 한 화면에서 확인한다.
- 최근 7일의 기록 상태, 운동 횟수, 총 운동 시간을 확인한다.
- 요약과 피드백은 사용자가 실제로 확인한 기록에만 근거한다.

MVP 핵심 기능은 정확히 다음 3개로 유지한다.

1. 자연어 식사·운동·휴식 기록 파싱 및 확인 후 저장
2. 일간 기록 요약과 근거 기반 한 줄 피드백
3. 최근 7일 운동·식사 패턴 리포트

## 3. MVP에 포함하지 않을 것

- 칼로리·영양소 등 복잡한 건강 분석
- Apple Watch를 포함한 웨어러블 연동
- 의료적 진단, 처방, 의학적 조언
- 자동 알림, 다중 계정, 소셜 기능
- 계획된 운동을 완료한 운동으로 집계하는 기능

## 4. 핵심 화면: 대시보드형 홈

### 상단

- LogFit 로고
- 안내 문구: `하루를 한 문장으로 기록하세요`

### 중앙 기록 영역

- 카카오톡처럼 자유롭게 문장을 입력하는 큰 기록창
- 저장 버튼
- 예시 안내: `오늘 점심은 김치찌개를 먹고 저녁에 요가 40분 했어.`

### 입력 후 확인 단계

저장 버튼을 누르면 AI가 원문에서 다음 기록을 추출해 확인 카드로 보여 준다.

- 식사: 식사 종류와 음식 내용
- 운동: 운동 종류와 사용자가 명시한 운동 시간
- 휴식: 사용자가 휴식했다고 명시한 경우
- 원문: AI 결과의 근거가 된 입력 문장

사용자는 각 항목을 수정하거나 삭제한 뒤 최종 저장한다. 불확실한 값은 임의로 채우지 않고 빈 값으로 표시하거나 확인을 요청한다.

### 하단 오늘의 현황

- 식사 기록 수
- 기록된 운동 시간
- 오늘의 상태
  - `운동 기록 있음`
  - `휴식`
  - `미기록`
  - `확인 필요`

`휴식`은 사용자가 휴식 문장으로 직접 기록한 날이다. `미기록`은 아직 운동 여부를 확인하지 않은 날이다. 두 상태는 자동으로 같은 의미로 처리하지 않는다.

## 5. 주간 리포트

최근 7일을 요일별로 보여 준다.

각 날짜에는 다음 상태 중 하나를 표시한다.

- 운동 기록 있음
- 휴식
- 미기록
- 확인 필요
- 계획된 운동

계획된 운동은 사용자가 앞으로 하겠다고 쓴 계획이며 완료 운동으로 집계하지 않는다.

주간 집계에는 다음을 포함한다.

- 운동한 날짜 또는 운동 횟수
- 사용자가 명시한 운동 시간의 총합
- 운동 종류
- 식사 기록 건수
- 미기록일 수

운동 시간이 입력되지 않은 기록은 총 시간에 포함하지 않는다. 시간이나 운동 종류가 모호한 경우 임의 추정 대신 사용자 확인 대상으로 남긴다.

## 6. 피드백 원칙

- 오늘의 기록 요약을 먼저 보여 준다.
- 피드백은 오늘 기록과 최근 7일 집계에 근거한다.
- 기록에 없는 사실을 만들어 내지 않는다.
- 운동을 많이 한 다음 날의 휴식 권고나 식단 추천은 향후 확장 후보이며, 핵심 MVP에서는 기록 기반의 짧은 피드백을 우선한다.
- 불확실한 기록을 사실처럼 단정하지 않는다.

## 7. 사용자 흐름

1. 사용자가 홈 화면의 큰 입력창에 한 문장을 입력한다.
2. AI가 식사·운동·휴식 후보를 추출한다.
3. 사용자가 추출 결과를 확인하고 수정한다.
4. 사용자가 최종 저장한다.
5. 홈 화면의 오늘 현황이 갱신된다.
6. 오늘 요약과 근거 기반 피드백을 확인한다.
7. 주간 리포트에서 7일의 상태와 운동 집계를 확인한다.

## 8. 제약과 구현 범위

- LogFit은 7주차 공동 프로젝트 `platen`과 완전히 분리된 개인 프로젝트다.
- 작업 폴더는 `~/logfit-mvp`이며 `~/platen`의 파일·Git 설정·브랜치·원격 저장소를 수정하지 않는다.
- 개인 프로젝트는 단일 `index.html`을 중심으로 구성한다.
- CSS와 JavaScript는 `index.html` 안에 둔다.
- 구현은 실제 서버 연동 없이 로컬에서 재현 가능한 데모 범위로 한다. 구체적인 파싱 방식은 구현자가 정하되, 명세의 데이터 규칙을 지킨다.
- 외부 라이브러리는 추가하지 않는다.

## 9. 저장과 개인정보

- 사용자 기록은 브라우저 `localStorage`에 저장한다.
- 새로고침 후에도 최종 저장 기록과 일간·주간 리포트가 유지되어야 한다.
- CSV 내보내기는 검증을 위한 보조 기능으로 제공한다.
- 실제 개인 기록은 GitHub 저장소에 포함하지 않는다.
- 공개 저장소와 테스트에는 합성 샘플 데이터만 포함한다.
- 브라우저에 API 키를 넣지 않는다. 정적 배포로 안전하게 제공할 수 없는 AI 기능은 로컬 데모와 영상 증빙으로 제한한다.

## 10. 구현자에게 남기는 결정

- 기존 화면과 새 LogFit 대시보드의 공존 방식
- 자연어 추출을 시연하기 위한 프런트엔드 데이터 구조와 샘플 문장
- 확인 카드의 편집 UI 세부 형태
- 주간 리포트의 시각화 방식
- AI 연동 없이도 사용자가 흐름을 검증할 수 있는 데모 동작

## 11. 9주차 검증 계획

- 최소 3건 이상의 실제 실행 테스트를 수행한다.
- 복합 문장 파싱, 날짜 처리, 운동·휴식 상태, 주간 집계, 새로고침 후 데이터 유지를 검증한다.
- 각 테스트의 입력, 기대 결과, 실제 결과, 통과 여부를 문서화한다.
- 브라우저 데모 화면과 실행 결과를 증빙으로 남긴다.

검증 결과 문서는 `docs/verification-results.md`에 작성하고, 합성 테스트 데이터와 재현 가능한 검증 코드는 `tests/`에 둔다.

## 12. GitHub 제출 구조와 공개 계획

개인 공개 저장소 이름은 `logfit-mvp`로 계획한다. 저장소 생성, 공개 설정, 최초 push 전에는 사용자의 확인을 받는다.

제출 저장소에는 다음 파일을 포함한다.

- `README.md`: 문제 정의, 기능, 설치·실행 방법, 데모 링크, 검증 결과
- `LICENSE`: 프로젝트 공개 라이선스
- `.gitignore`: 비밀정보와 개인 데이터 제외
- `.env.example`: 필요한 환경변수의 예시만 작성
- `AGENT_LOG.md`: Hermes 지시·결과·사람의 확인·수정 기록
- `tests/`: 재현 가능한 검증 코드 및 합성 테스트 데이터
- `docs/`: 설계 문서와 구현 결과 설명

README만 보고 다른 사람이 실행할 수 있게 한다. 가능하면 GitHub Pages에 정적 웹앱을 배포한다. GitHub 주소, 데모 주소 또는 영상, 검증 결과는 9주차 제출 슬라이드에 포함한다.

## 13. 기록 데이터 규칙

- 한 문장에 여러 식사·운동·휴식 정보가 포함되면 각각 독립된 기록으로 분리한다.
- 각 기록은 고유 ID와 유형을 가지며, 원본 입력 문장 `raw_text`를 보존한다.
- 식사 시간대와 운동 시간이 입력되지 않았으면 임의로 추정하지 않는다. 활동 날짜가 없는 완료 기록은 입력 당일 날짜를 기본값으로 표시하고 저장 전에 사용자에게 확인받는다.
- 계획된 운동과 실제 완료된 운동을 구분한다. 계획된 운동은 완료 운동 집계에 포함하지 않는다.
- 휴식, 미기록, 확인 필요 상태를 구분한다.
- AI 추출 결과를 사용자가 확인하고 수정한 뒤에만 최종 저장한다.
- 운동 시간 합계는 실제 완료된 운동 중 시간이 확인된 값만 합산한다.
- 한 번의 입력으로 들어온 식사·운동·휴식 기록도 각각 독립된 CSV 행으로 저장한다.

예시: `아침 샐러드, 점심 김치찌개, 저녁 요가 40분`은 식사 2건과 운동 1건으로 분리한다.

## 14. 날짜와 시간 규칙

- 기준 시간대는 `Asia/Seoul`(KST)이다.
- 활동일은 `record_date`, 실제 입력 시각은 `created_at`으로 별도 저장한다.
- 날짜가 없는 완료된 식사·운동·휴식 기록은 입력 당시의 KST 날짜를 `record_date` 기본값으로 사용한다. 저장 전에 사용자에게 날짜를 보여 준다.
- `어제`, `그저께`, `지난주 월요일`과 같은 상대 날짜는 입력 당시의 KST 날짜를 기준으로 계산한다.
- `주말에`, `며칠 전에`처럼 날짜가 불명확한 표현은 `확인 필요` 상태로 두고 사용자에게 확인받는다.
- 미래 날짜의 활동은 계획으로 분류하며 실제 완료 운동 횟수와 운동 시간에 포함하지 않는다.
- 주간 집계는 `created_at`이 아니라 `record_date`를 기준으로 수행한다.
- 테스트에서는 기준 날짜와 시간을 고정해 같은 입력이 같은 결과를 내는지 검증한다.

## 15. 대표 상태와 집계 우선순위

- 식사·운동·휴식 기록은 같은 날에도 서로 독립적으로 보존하고 집계한다.
- 실제 완료된 운동 기록이 하나라도 있으면 홈 화면의 대표 상태를 `운동 완료`로 표시한다.
- 완료된 운동이 없고 명시적인 휴식 기록만 있으면 대표 상태를 `휴식`으로 표시한다.
- 완료된 운동과 휴식이 함께 있으면 대표 상태는 `운동 완료`로 표시하되 상세 기록에는 둘 다 보여 준다.
- 계획된 운동만 있으면 대표 상태를 `운동 예정`으로 표시하며 완료 집계에서는 제외한다.
- 기록 자체가 없으면 `미기록`으로 표시하고 휴식으로 추정하지 않는다.
- 완료 여부가 불확실하면 `확인 필요`로 표시하며 완료 집계에서 제외한다.
- 독립된 실제 완료 운동 기록 1건을 운동 1회로 집계한다.
- 운동 시간이 누락된 완료 운동은 운동 횟수에는 포함하고 총 운동 시간에서는 제외한다. 해당 기록에는 `시간 미입력`을 표시한다.
- 식사 기록 수는 운동·휴식 상태와 독립적으로 집계한다.

## 16. 저장 지속성

- 사용자가 최종 확인 후 저장한 기록은 브라우저 새로고침 뒤에도 유지되어야 한다.
- MVP에서는 브라우저의 로컬 저장소를 사용해 기록과 수정 결과를 보존한다.
- 입력 중인 원문과 아직 확인하지 않은 추출 결과는 최종 저장 기록과 분리하며, 새로고침 시 복구를 보장하지 않는다.
